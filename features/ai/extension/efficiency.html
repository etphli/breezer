Less repeated work

The changes behind the measurements, and the work still ahead.

What we changed to reduce work

Combined 1.2.0 candidate, not yet released. Measured on one M1 Mac against the installed Breezer and Chrome.

Most of this work removes repeated effort. It did not make the whole browser faster, and some results got worse.

Saved tabs

Restoring saved tabs used to compare each open tab with every saved record. It now builds a lookup index once per operation, and the sidebar model uses an index of saved entries too. With 1,000 synthetic saved records, matching fell from 190.0 ms to 2.9 ms and model building from 3.30 ms to 0.19 ms. That is JavaScript work on stored records, not 1,000 live tabs or overall browser speed.

Less idle work

Sidebar rows keep their elements when nothing visible changed, so keyboard focus stays put. Organato’s helper starts on first request, is shared between pages and exits when idle. The updater helper is also released when idle, and AI provider code loads only when needed. Built-in filter lists can load from checked, prepared copies, with the normal compiler as fallback. The build also used Chromium’s Apple Silicon profile-guided optimization (PGO). None of these was measured alone in the browser comparison, so none gets individual credit.

What improved, and what was already there

Against the installed Breezer, the first local page load after opening and closing tabs fell from 717.4 ms to 262.2 ms. Chrome took 52.4 ms, so the pause is shorter but not gone. New tabs (98.8 ms against Chrome’s 198.7 ms) and reopening an existing profile (861.3 ms against 1,070.2 ms) stay faster than Chrome, but the installed Breezer already had that lead.

What got worse

Two results regressed. Typical local navigation rose to 48.9 ms, against 33.9 ms for the installed Breezer and 33.1 ms for Chrome. Summed process memory (RSS) with ten tabs reached 2,756.1 MiB, against 2,560.8 MiB and 2,515.1 MiB. With one tab, RSS matched Chrome but exceeded the installed Breezer. The macOS memory footprint barely moved. CPU readings were too small to measure reliably, so there is no CPU or battery claim.

Still to do

Next: find the causes of the navigation and memory regressions, trace the remaining first-load pause and get a valid Chrome footprint. Feature acceptance and the signed release build are also unfinished.

How these numbers were measured

  • Browser results: medians from six balanced rounds on one Apple M1 Mac on AC power, with 36 scored launches. Startup uses initialized or reused profiles, not a cold boot. Navigation uses a local test page, not general websites. Six rounds show medians and ranges, not statistical significance.
  • RSS adds up each process’s resident memory and can count shared pages more than once. Chrome’s macOS footprint is unavailable because some of its samples failed identity checks.
  • Saved-tab figures come from a separate synthetic test: six alternating rounds comparing the previous and new saved-tab code.
  • The candidate is a private, ad hoc signed build. Its app metadata still reads 0.20.1.1. Full feature checks and the release build are pending.
  • Evidence: docs/efficiency-1.2.0.md in the Breezer source.
